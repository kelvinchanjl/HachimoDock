# Grok Bot 按键语音

本适配器把哈基米的按键语音写进用户已经打开的 Grok Bot 桌面对话。它使用现有语音识别，不调用 xAI 模型 API，也不接入 Grok Bot 的记忆、工具或云端电脑。公开文档没有提供这类对话接口，也没有提供可引用的窗口或输入框标识，因此这里不会按应用名或包名搜索，也不会向当前任意窗口打字。

## 实际行为

1. 在渠道里选择 Grok Bot。这个渠道不会因为扫到某个进程而显示为已安装。
2. 打开要发送的那条对话，点中它的输入框。
3. 在语音面板先读取当前前台输入框，核对系统返回的应用名和窗口标题，再确认登记。登记只保存在本次应用运行的内存里，重启后要重新登记。
4. 按住设备的录音键，音频仍走现有识别流程。
5. 松开后，只有已登记的输入框仍是前台焦点时，才把识别文字追加进去。松开不会发送。
6. 另一次短按确认键或摇杆，才会向同一个输入框发送。识别文字为空、还没写入、焦点变了，或读不到输入框内容时，都不发送，也不自动重试。

焦点、窗口标题、进程或控件身份有任何一项对不上，操作会停下来并保留原来的文字。切换对话后如果窗口标题或输入框身份变了，必须重新登记。如果 Grok Bot 在同一窗口里更换对话却不改变标题和输入框身份，本适配器无法发现这次更换，此时不要发送，先重新登记。

## 系统和权限

Grok Bot 桌面应用本身支持 macOS（Apple 芯片和 Intel）、Windows（x64 和 Arm64）以及 Linux（x64 和 Arm64）。依据是官方说明：[Get started](https://docs.x.ai/grok-bot/get-started) 和 [Deploy Grok Bot](https://docs.x.ai/grok-bot/deployment)。

本适配器只在 macOS 和 Windows 上写入输入框：

- macOS 使用系统辅助功能读取当前焦点，并用指向该进程的按键追加文字。权限必须事先已经授予。登记和写入都不会弹出授权，也不会打开系统设置。
- Windows 使用 UI Automation 读取当前焦点。追加前会保存并在结束后恢复剪贴板。只有焦点仍是已登记控件时才粘贴。发送前还要能读到输入框文字，并确认它仍以本次识别文字结尾。
- Linux 版 Grok Bot 可以安装，但哈基米没有对应的无障碍输入桥。选择该渠道时会直接拒绝，不会向窗口输入。

手机应用不在范围内。

## 语音识别配置

识别和合成仍使用「API 配置」里现有的语音服务，和 Grok Bot 登记分开保存。0.1.237 的自定义 OpenAI 兼容示例是 `http://127.0.0.1:8766/v1`，识别模型 `whisper-base`，合成模型 `cosyvoice-300m-sft`，密钥为空。本适配器不填写、不生成、也不建议填入虚假密钥。本地服务没启动，或该服务实际上要求密钥时，识别会在写入前失败。回复播报不在这次改动里。

## 手动验收

自动化测试只覆盖目标匹配、焦点变化、空文本、确认条件和剪贴板恢复约束。下面这些还没有在真实设备、真实 Grok Bot 或实体按键上执行：

1. 在 macOS 或 Windows 上安装并登录 Grok Bot，打开一条具体对话。
2. 手动授予哈基米辅助功能权限（仅 macOS 需要；应用不会代为打开）。
3. 配好并且能单独完成一次语音识别。
4. 登记该对话的输入框，核对应用名和窗口标题。
5. 按住录音并松开，确认文字只出现在该输入框，剪贴板原内容还在，消息没有发出。
6. 把焦点切到别的窗口后再松开，确认没有文字写入。
7. 回到已登记输入框，短按确认键或摇杆，确认只发送这一条非空草稿。
8. 换一条对话后不重新登记，确认发送被拒绝。

## 仍缺的信息

- 用户实际使用的操作系统。
- 一个公开、稳定、能区分某条对话输入框的辅助功能标识。没有它之前，只能依赖用户登记的当前焦点。
- 本机语音服务是否已在 `127.0.0.1:8766` 运行，以及它是否接受空密钥。
